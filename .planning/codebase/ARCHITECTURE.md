# Architecture

**Analysis Date:** 2026-04-12

## Overview

This is a documentation and knowledge management project for the **西南大学信息化项目全生命周期管理系统** (Southwest University Informatization Project Lifecycle Management System). The system architecture is split across two Git repositories — a code repo and a wiki repo — managed under a shared parent directory. It also includes a knowledge graph layer generated by the `graphify` tool.

The product itself is a browser-runnable HTML demo (no build toolchain) implementing a lifecycle management platform covering six business modules: 需求征集 → 立项论证 → 项目招采 → 项目实施 → 项目验收 → 项目运维.

## Core Components

**my-project-code/ — Code Repository**
- Houses the HTML demo application, all runnable directly in a browser with no server required.
- Contains the `openspec/` change management system, which is the canonical workflow for proposing, designing, generating, and archiving feature changes.
- Shared JS modules (`core.js`, `data.js`, `nav.js`, `style.css`) underpin all views.
- Individual view JS files (`views/approval.js`, `views/demand.js`, `views/notification.js`, etc.) implement each page's UI logic.
- UI specifications live in `doce/ui-spec.md` (shadcn/ui style, Tailwind CSS + Lucide Icons via CDN).

**my-project-wiki/ — Wiki Knowledge Base**
- An Obsidian vault organized into `raw/` (read-only source documents) and `wiki/` (maintained knowledge pages).
- `wiki/` is the writable knowledge layer: entities, concepts, sources, decisions, and synthesis pages.
- `raw/` stores ingested source material: regulation documents, meeting notes, design specs, contract templates, and archived OpenSpec files. These are never modified.
- Managed by AI following the Wiki Schema defined in `my-project-wiki/CLAUDE.md`.

**graphify-out/ — Knowledge Graph**
- Auto-generated by the `graphify` Python tool from all markdown files across both repositories.
- Outputs: `GRAPH_REPORT.md` (community structure, god nodes, knowledge gaps), `graph.json`, `graph.html` (interactive visualization).
- 236 nodes, 308 edges, 23 detected communities as of the last build.
- Used as a pre-read before answering architecture or codebase questions.

**OpenSpec Workflow — Change Management Layer**
- A structured, AI-assisted spec-driven workflow for all feature changes to the demo.
- Each change lives in `my-project-code/openspec/changes/[change-name]/` as four documents: `proposal.md`, `design.md`, `spec.md`, `tasks.md`.
- After archiving (`/opsx:archive`), change files are synced to `my-project-wiki/raw/openspec/` and ingested into the wiki.

**Cross-repo synchronization flow:**
1. Feature change proposed and implemented in `my-project-code/openspec/changes/`.
2. After archiving, change files copied to `my-project-wiki/raw/openspec/` via `cp -r`.
3. Wiki operator runs `/ingest` on the synced files to extract decisions and update concept pages.
4. `graphify` is run to rebuild the knowledge graph reflecting new content.

## Design Patterns

**Spec-Driven Development (OpenSpec)**
All changes to the demo must pass through the four-phase OpenSpec workflow (propose → apply → archive → wiki sync) before code is written. Direct AI-generated pages without a proposal are explicitly forbidden per `my-project-code/CLAUDE.md`.

**Wiki as Structured Knowledge Layer**
The wiki separates raw source material (`raw/`) from synthesized knowledge (`wiki/`) with strict read-only enforcement on raw files. This preserves document provenance while enabling AI-maintained structured knowledge pages.

**Layered JS Architecture (Demo Application)**
The demo follows a layered module pattern:
- `core.js` — shared utilities and business logic functions
- `data.js` — centralized mock data layer
- `nav.js` — navigation rendering and highlighting
- `views/*.js` — per-module view renderers (one file per module: approval, demand, notification, finance, system, review, expert, logs, acceptance, project, dashboard)

**Knowledge Graph as Architecture Oracle**
`graphify-out/GRAPH_REPORT.md` is treated as a first-read before architectural questions. God nodes (highest connectivity) represent the system's core abstractions: `系统规则表（43条硬规则）`, `需求征集模块`, `项目验收模块`.

## Key Architectural Decisions

**Two-repo split (code + wiki)**
The code repo handles the runnable demo and its change workflow; the wiki repo handles all accumulated knowledge. This prevents knowledge artifacts from polluting the deliverable codebase and vice versa.

**No build toolchain**
The demo is plain HTML with CDN-loaded Tailwind CSS and Lucide Icons. Files are opened directly in a browser. This minimizes infrastructure complexity appropriate for a demo/prototype phase.

**Static mock data**
All demo data is static JavaScript mocks defined in `data.js`. No backend, no persistence. The OpenSpec for `notification-template` explicitly states "不新增模板的增删改持久化（Demo 阶段，数据为静态 mock）".

**Raw files are immutable**
`raw/` in the wiki is never modified. Outdated files receive an `-archived` suffix. This ensures provenance tracing from wiki knowledge back to original source documents.

**Obsidian-compatible internal linking**
All wiki internal links use `[[页面名]]` format for Obsidian compatibility, enabling graph view and backlink navigation within the vault.
