## 一、系统总体架构概览

  

### 1.1 系统定位

  

本系统是面向西南大学信息化建设办公室（信息办）及各二级单位（项目用户单位）的**信息化项目全生命周期管理平台**，以《西南大学信息化项目管理办法（试行）》为制度蓝本，将纸面制度转化为可执行、可监控、可追溯的数字化工作流。

  

### 1.2 全局角色体系

  

| 角色 | 对应机构 | 核心权限 |

|---|---|---|

| 系统管理员 | 信息办 | 全局配置、角色管理、流程引擎维护 |

| 信息办专员 | 信息办 | 需求征集发布、初筛、组织论证、审核、验收组织、运维监管 |

| 信息办领导 | 信息办 | 审批、决策看板、报告导出 |

| 领导小组成员 | 数智化建设领导小组 | 重大项目审定、成效评估、全局看板 |

| 领导小组办公室 | 挂靠党政办与信息办 | 中/小/微型项目审定、进度监控 |

| 二级单位经办人 | 项目用户单位 | 需求申报、项目实施管理、验收初验、运维管理 |

| 二级单位负责人 | 项目用户单位 | 内部审批、签字确认 |

| 采购专员 | 采购与招投标管理中心 | 采购文件编制、采购执行、合同管理 |

| 财务专员 | 财务部 | 预算审核、资金支付、经费监督 |

| 专家（校内/校外） | 外部/内部 | 参与论证、验收评审 |

  

### 1.3 全局流程总览

  

```

需求征集 → 初筛遴选 → 立项申报 → 论证评审 → 立项审批 → 立项下达

    → 采购调研 → 采购执行 → 合同签订 → 项目实施 → 进度监控

    → 内部初验 → 正式验收 → 项目移交 → 运维管理 → 项目评估

```

  

每一步均可触发 **终止流程**（第三十四条至第三十六条）。

  

### 1.4 项目分级自动判定引擎

  

系统在**项目创建时自动判定级别**，并据此驱动差异化流程：

  

| 级别 | 预算金额 | 采购方式 | 论证专家数 | 审定机构 | 汇报频率 |

|---|---|---|---|---|---|

| 重大 | >200万 | 政府公开招标 | ≥5（含校外） | 领导小组 | 每周 |

| 中型 | 100-200万 | 政府竞争性磋商/谈判/单一来源/合作创新 | ≥5（含校外） | 领导小组办公室 | 每周 |

| 小型 | 20-100万 | 非政府采购（询比/磋商/谈判/直接采购） | ≥3 | 领导小组办公室 | 每半月 |

| 微型 | <20万 | 信息办审批后自行采购 | ≥3 | 领导小组办公室（备案） | 按需 |

## 二、第一步：需求征集模块

  

### 2.1 业务流程

  

```

信息办发布征集通知 → 二级单位填报需求 → 单位内部决策会审议

    → 提交《需求申请表》 → 信息办汇总 → 系统自动初筛

    → 人工复核初筛结果 → 输出通过/未通过清单

```

  

### 2.2 功能模块详细设计

  

#### 2.2.1 征集通知发布（信息办操作）

  

**功能点：**

- 信息办专员创建征集批次，填写征集年度、征集时间段、征集说明

- 系统自动向所有二级单位负责人及经办人发送站内通知 + 邮件通知

- 支持附件上传（征集通知文件模板）

- 征集状态管理：未开始 / 征集中 / 已截止 / 已完成

  

**界面设计要素：**

- 顶部：征集批次管理列表（年度、状态、创建时间、操作）

- 新建征集表单：年度选择、征集起止日期、征集说明（富文本）、附件上传

- 底部：确认发布按钮

  

#### 2.2.2 需求填报（二级单位经办人操作）

  

**功能点：**

- 经办人在线填写《信息化项目建设需求申请表》（对应第十二条）

- 表单字段：

  

| 字段 | 类型 | 必填 | 说明 |

|---|---|---|---|

| 项目名称 | 文本 | 是 | — |

| 所属单位 | 下拉选择 | 是 | 自动关联当前用户单位 |

| 项目类别 | 下拉选择 | 是 | 基础设施/硬件设备/信息系统/数字资源/运维服务 |

| 项目优先级 | 数字输入 | 是 | 同批次内排序 |

| 建设目标 | 富文本 | 是 | — |

| 主要建设内容 | 富文本 | 是 | — |

| 预估预算（万元） | 数字 | 是 | 用于自动分级 |

| 建设周期（月） | 数字 | 是 | — |

| 牵头业务部门 | 文本 | 是 | — |

| 分管领导 | 文本 | 是 | — |

| 需求背景与依据 | 富文本 | 是 | 说明为什么需要建设 |

| 现有系统情况 | 富文本 | 否 | 与现有系统的关系 |

| 附件 | 文件上传 | 否 | 支持支撑材料 |

  

- **单位内部决策会审议**：经办人提交后，流转至二级单位负责人审批。负责人审批时需填写"是否经单位决策会议审议通过"（是/否）及会议纪要编号。

- **多项目排序**：同一单位同一征集批次提交多个项目时，支持拖拽排序。

  

**界面设计要素：**

- 左侧：征集批次信息卡片（年度、截止时间倒计时）

- 中部：需求表单（分步骤：基本信息 → 建设内容 → 预算与周期 → 附件）

- 右侧：已提交需求列表（状态追踪）

- 底部：保存草稿 / 提交审批

  

#### 2.2.3 系统自动初筛（系统自动执行）

  

**功能点：**

基于第十三条的六项规则，系统在需求提交后自动执行初筛逻辑：

  

| 规则编号 | 初筛规则 | 系统实现方式 |

|---|---|---|

| (一) | 已启动建设或已建成并正常运行的项目，再次报送且无正当理由 | 系统自动匹配历史项目库，检查是否存在同名或高度相似的已建/在建项目。如有，标记为"疑似重复"，需经办人补充说明正当理由 |

| (二) | 需求不明确、不合理，市场调研不充分，预算严重背离实际，无法确定牵头部门或分管领导 | 系统检查必填字段完整性（目标、内容、预算、牵头部门、分管领导）。预算合理性由后续专家论证判断，此处仅做格式校验 |

| (三) | 与现有系统功能或数字资源有较大重叠且无正当理由 | 系统维护现有系统功能标签库，需求填报时可关联现有系统。如关联度>阈值且无差异说明，标记为"疑似重叠" |

| (四) | 建设理念和技术路线已过时或被淘汰 | 系统维护"技术过时关键词库"（由信息办定期更新），自动扫描需求描述。命中则标记为"技术路线存疑" |

| (五) | 已被否决且无新理由支持再次论证 | 系统自动匹配历史被否决项目库，检查是否有相同/相似需求。如有，检查是否有新的支撑理由 |

| (六) | 不符合学校其他相关规定 | 预留接口，可接入学校其他合规规则引擎 |

  

**初筛结果处理：**

- **通过**：进入人工复核环节

- **标记疑似**：需经办人补充说明，信息办人工复核后决定通过/驳回

- **不通过**：直接驳回，系统自动通知经办人并说明原因

  

**界面设计要素（信息办视角）：**

- 初筛结果看板：总需求数 / 通过数 / 疑似数 / 驳回数

- 疑似项目列表：可查看疑似原因、经办人补充说明、人工复核操作

- 驳回项目列表：可查看驳回原因、支持申诉操作

  

#### 2.2.4 人工复核与遴选（信息办操作）

  

**功能点：**

- 信息办专员对自动初筛通过及疑似复核通过的需求进行人工复核

- 复核内容：需求合理性、与学校战略规划的契合度、与现有系统的差异性

- 复核结果：通过 / 驳回（需填写驳回理由）

- 支持批量操作

- 输出《需求遴选结果汇总表》，可导出

  

**界面设计要素：**

- 需求卡片列表：项目名称、单位、类别、预算、初筛状态、操作按钮

- 详情弹窗：完整需求信息、初筛结果、历史项目对比、复核操作区

- 批量操作栏：批量通过、批量驳回

  

### 2.3 数据模型

  

```

征集批次表 (collection_batch)

├── batch_id (主键)
```

## 三、第二步：立项论证模块

  

### 3.1 业务流程

  

```

通过遴选的需求 → 经办人填报《申报书》+ 建设方案 → 信息办审核申报材料

    → 信息办组织专家论证 → 专家评审 → 形成论证意见

    → 确定拟建项目及优先级 → 领导小组/办公室审定

    → 信息办下达立项通知书

```

  

### 3.2 功能模块详细设计

  

#### 3.2.1 项目申报书填报（二级单位经办人）

  

**功能点：**

- 经办人基于已通过遴选的需求，填报《信息化项目建设申报书》（对应第十四条）

- 需制定详细的**建设方案**，包含：

  

| 方案模块 | 内容要求 | 对应条款 |

|---|---|---|

| 建设目标 | 明确、可量化的目标描述 | 第十四条 |

| 建设内容 | 详细的功能模块、技术组件清单 | 第十四条 |

| 业务需求 | 业务流程现状与优化目标 | 第十四条 |

| 技术方案 | 技术架构、选型依据、部署方案 | 第十四条 |

| 采购清单及预算 | 详细的软硬件清单、单价、总价 | 第十四条 |

| 实施人员 | 项目负责人、核心成员、职责分工 | 第十四条 |

| 实施计划 | 甘特图或里程碑计划 | 第十四条 |

| 采购需求调查 | 充分的市场调研结果 | 第十四条 |

  

- 系统提供**结构化模板**引导填报，支持附件上传

- 填报完成后流转至二级单位负责人审批

  

**界面设计要素：**

- 左侧：步骤导航（基本信息 → 建设方案 → 采购清单 → 实施计划 → 附件）

- 中部：表单填写区

- 右侧：申报进度条、当前状态、操作日志

- 采购清单：支持逐行添加（品名、规格、数量、单价、小计），自动汇总总价

- 甘特图组件：可视化编辑里程碑计划

  

#### 3.2.2 采购需求调研管理（二级单位经办人）

  

**功能点：**

- 支持在线管理供应商/服务商调研记录（对应第二十四条）

- 非单一来源采购的，至少填写3家供应商的调研信息

- 调研记录字段：

  

| 字段 | 说明 |

|---|---|

| 供应商名称 | — |

| 联系方式 | — |

| 产品/服务概述 | — |

| 报价（万元） | — |

| 典型案例/用户评价 | 有软件的需调研产品使用单位用户情况 |

| 优势与不足 | — |

| 调研方式 | 现场考察/电话调研/资料调研 |

| 调研人/日期 | — |

  

- 自动生成《调研情况对比报告材料》

  

#### 3.2.3 论证组织（信息办操作）

  

**功能点：**

  

**A. 专家库管理：**

- 系统维护校内专家库和校外专家库

- 专家信息：姓名、单位、专业领域、联系方式、参与次数、评价

- 支持按专业领域筛选专家

  

**B. 论证会议安排：**

- 信息办创建论证会议，选择待论证项目

- 系统根据项目级别自动提示专家人数要求：

  

| 项目级别 | 专家人数 | 特殊要求 |

|---|---|---|

| 重大/中型 | ≥5人 | 须含校外专家 |

| 小型/微型 | ≥3人 | — |

| 重大（含100万以上设备） | — | 须有实验室建设与设备管理处人员列席 |

| 重大 | — | 须有财务部人员列席 |

  

- 系统自动校验专家组成是否合规，不合规时给出预警

- 论证会议信息：时间、地点、参会专家、列席人员、议程

  

**C. 论证材料分发：**

- 论证前，系统自动将项目申报书、建设方案、调研报告等材料推送至专家账号

- 专家可在线预览、批注

  

#### 3.2.4 专家评审（专家操作）

  

**功能点：**

- 专家在线查看项目材料

- 填写《专家论证意见表》，评估维度（对应第十五条）：

  

| 评估维度 | 评分（1-5） | 文字意见 |

|---|---|---|

| 建设必要性 | — | — |

| 技术可行性 | — | — |

| 技术先进性 | — | — |

| 安全性 | — | — |

| 方案科学性 | — | — |

| 人员和进度安排合理性 | — | — |

| 预算合理性 | — | — |

| 与战略规划的契合度 | — | — |

  

- 支持"通过/修改后通过/不通过"的总体结论

- 论证会议后，系统汇总所有专家意见，生成《论证意见汇总表》

  

**界面设计要素：**

- 左侧：项目材料浏览区（申报书、方案、调研报告）

- 右侧：评审打分表单

- 底部：提交评审意见按钮

  

#### 3.2.5 论证结果处理（信息办操作）

  

**功能点：**

- 系统汇总专家意见，形成论证结论：**通过 / 修改后通过 / 不通过**

- **通过**：确定项目优先级，进入审批环节

- **修改后通过**：经办人按意见修改后重新提交，信息办确认

- **不通过**：项目退回。**二次论证仍未通过的，系统自动锁定该项目，一年后方可重新提交**（对应第十六条）

- 重大项目提交**领导小组**审定（对应第十九条）

- 中/小/微型项目提交**领导小组办公室**审定（对应第十九条）

  

#### 3.2.6 立项审批（决策机构操作）

  

**功能点：**

- 系统根据项目级别自动路由至对应审批节点

- 审批界面展示：项目概览、论证意见汇总、预算明细、建议优先级

- 审批结果：批准 / 驳回 / 退回修改

- 批准后，系统自动进入立项下达流程

  

**特别立项通道（对应第二十一条）：**

- 支持"上级部门要求"、"突发状况应对"、"学校决策会议研究决定"等特殊立项通道

- 预算<5万的项目，经信息办审批后可直接立项

- 系统记录特殊立项依据

  

#### 3.2.7 立项通知书下达（信息办操作）

  

**功能点：**

- 系统根据审批结果和经费下达情况，自动生成《立项通知书》

- 通知书内容：项目名称、编号、级别、批准预算、建设周期、项目负责人、关键里程碑

- 系统自动通知二级单位经办人和负责人

- **自动失效机制**：项目自正式立项之日起**半年内未启动采购**或**一年内未签订合同**，系统自动标记为"失效"，需重新论证（对应第二十二条）

  

#### 3.2.8 通用基础硬件设施管理（对应第二十三条）

  

**功能点：**

- 涉及服务器、存储、网络等通用基础硬件的项目，二级单位**只预算其他建设内容的经费**

- 系统提供"基础硬件资源申请"入口，二级单位按需申请

- 信息办在线审核、批准后，根据具体需求和参数配置分配资源

- 系统维护基础硬件资源池（可用资源、已分配资源、使用率）

## 四、第三步：项目招采模块

  

### 4.1 业务流程

  

```

立项下达 → 采购调研（如未完成）→ 采购文件编制 → 提交信息办技术审核

    → 采购执行（按级别选择采购方式）→ 确定承建/服务厂商

    → 合同拟定 → 提交信息办合同审核 → 签订合同 → 合同备案

```

  

### 4.2 功能模块详细设计

  

#### 4.2.1 采购文件编制（二级单位经办人 + 采购专员）

  

**功能点：**

- 二级单位根据论证通过的申报书准备采购文件

- 系统提供采购文件模板（根据项目类别和级别自动匹配）

- 采购文件需包含：技术规范、商务要求、评分标准、接口标准、安全防护要求、数据治理与对接共享要求

- 采购文件与调研对比报告材料**一并提交信息办审核**（对应第二十五条）

  

**界面设计要素：**

- 左侧：项目基本信息卡片（项目名称、编号、级别、预算）

- 中部：采购文件编辑区（分章节：技术部分、商务部分、评分标准）

- 右侧：附件管理（调研报告、申报书参考）

- 底部：提交信息办审核按钮

  

#### 4.2.2 采购文件技术审核（信息办操作）

  

**功能点：**

- 信息办重点审核（对应第二十五条）：

  - 技术规范是否与建设方案一致

  - 接口标准是否符合学校统一规范

  - 安全防护要求是否充分

  - 数据治理和对接共享需求是否明确

- 审核结果：通过 / 退回修改（需填写修改意见）

- 审核通过后，采购文件方可进入采购执行环节

  

#### 4.2.3 采购执行管理

  

**功能点：**

- 系统根据项目级别自动匹配采购方式（对应第十条）：

  

| 级别 | 采购方式 | 执行主体 |

|---|---|---|

| 重大 | 政府采购公开招标 | 采购与招投标管理中心 |

| 中型 | 竞争性磋商/谈判/单一来源/合作创新 | 采购与招投标管理中心 |

| 小型 | 非政府采购（挂网：询比/磋商/谈判/直接采购） | 采购与招投标管理中心 |

| 微型 | 信息办审批后自行采购 | 二级单位自行组织 |

  

- 采购过程状态跟踪：采购文件发布 → 投标/响应 → 评审 → 中标公示 → 确定厂商

- 支持上传各阶段文档（招标文件、投标文件、评审报告、中标通知书等）

- 采购结果自动关联至项目信息

  

**界面设计要素：**

- 采购流程时间线：可视化展示各阶段状态和时间节点

- 文档管理区：按阶段分类管理采购文档

- 中标信息卡片：中标单位、中标金额、项目经理

  

#### 4.2.4 合同管理（二级单位经办人 + 信息办）

  

**功能点：**

  

**A. 合同拟定：**

- 系统提供合同模板，自动填充项目信息、中标信息

- 合同关键条款：

  

| 条款 | 说明 |

|---|---|

| 建设内容 | 与采购文件/申报书一致 |

| 建设周期 | **原则上不超过2年**（对应第二十六条） |

| 数据治理集成与互联共享要求 | 明确数据标准、接口规范、共享义务 |

| 付款方式 | 与项目进度挂钩 |

| 维保年限 | 明确质保期和维保服务内容 |

  

**B. 合同审核：**

- 拟签合同提交信息办审核（对应第二十六条）

- 审核重点：建设内容、建设周期、数据治理集成与互联共享要求、付款方式、维保年限

- 审核结果：通过 / 退回修改

  

**C. 合同签订与备案：**

- 审核通过后方可签订合同

- 签订后上传合同扫描件至系统备案

- 系统自动记录**合同签订日期**，启动建设周期监控

  

**D. 建设周期预警：**

- 系统以合同签订日期为起点，监控建设进度

- 建设周期接近2年时，系统自动预警

## 五、第四步：项目实施模块

  

### 5.1 业务流程

  

```

合同签订 → 组建工作小组 → 制定实施计划 → 项目启动

    → 阶段性实施（调研→设计→部署→试运行）

    → 定期进度汇报 → 变更/延期管理 → 验收准备

```

  

### 5.2 功能模块详细设计

  

#### 5.2.1 工作小组组建（二级单位 + 信息办）

  

**功能点：**

- 合同签订后，二级单位与信息办共同组建项目工作小组（对应第二十七条）

- 工作小组信息：

  

| 角色 | 来源 | 职责 |

|---|---|---|

| 项目分管领导 | 项目用户单位 | 总体决策 |

| 项目负责人 | 项目用户单位 | 日常管理 |

| 信息办分管领导 | 信息办 | 技术指导 |

| 信息办对接人 | 信息办 | 日常监督 |

| 承建方项目经理 | 厂商 | 技术实施 |

  

- 系统记录工作小组成员及联系方式，建立项目沟通群组

  

#### 5.2.2 实施计划管理

  

**功能点：**

- 二级单位制定详细的项目实施计划（对应第二十七条）

- 计划需明确：各阶段任务分工、协同方式、时间节点、质量要求

- 阶段划分：

  

| 阶段 | 关键任务 | 交付物 |

|---|---|---|

| 项目启动 | 启动会、需求确认 | 启动会纪要、需求确认书 |

| 需求调研 | 详细需求调研、业务流程梳理 | 需求规格说明书 |

| 方案设计 | 技术方案设计、UI/UX设计 | 设计方案文档 |

| 开发/部署 | 系统开发、环境部署、集成测试 | 测试报告 |

| 试运行 | 系统上线试运行、用户培训 | 试运行报告、培训记录 |

| 验收准备 | 文档整理、问题整改 | 验收申请材料 |

  

- 支持甘特图可视化编辑和查看

- 支持关键里程碑设置和提醒

  

**界面设计要素：**

- 甘特图视图：可切换列表/甘特图两种模式

- 里程碑标记：红色标记关键节点

- 进度百分比：每个阶段自动计算完成度

- 拖拽调整：支持拖拽调整任务时间

  

#### 5.2.3 进度汇报管理

  

**功能点：**

- 系统根据项目级别自动设定汇报频率（对应第二十八条）：

  

| 项目级别 | 汇报频率 | 汇报对象 |

|---|---|---|

| 重大/中型 | 每周 | 项目用户单位 + 信息办 |

| 小型 | 每半月 | 项目用户单位 + 信息办 |

| 微型 | 按需 | 备案 |

  

- 承建方定期填写进度汇报，内容包括：

  - 本周/半月完成工作

  - 下周/半月计划工作

  - 存在问题及风险

  - 需协调事项

- 二级单位和信息办可在线查看、批注、督办

- **重大/中型项目及关注度高的小型项目**：信息办和二级单位各自分工记录项目实施中的问题及解决情况，**每月向分管校领导汇报，每季度向领导小组汇报**（对应第三十条）

- 系统自动生成月度/季度汇报模板

  

**界面设计要素：**

- 进度汇报时间线：按时间倒序排列所有汇报记录

- 汇报填写表单：结构化字段（完成工作、计划工作、问题、风险、需协调事项）

- 问题跟踪看板：列出所有待解决问题及处理状态

- 月度/季度报告自动生成按钮

  

#### 5.2.4 变更管理

  

**功能点：**

- 严格控制项目变更（对应第三十二条）

- 变更申请流程：

  

```

经办人提交变更申请 → 填写变更缘由 → 提交变更后方案

    → 信息办审核 → 专家论证（如需）→ 审批通过 → 实施变更

```

  

- 变更申请字段：

  

| 字段 | 说明 |

|---|---|

| 变更类型 | 建设内容变更 / 技术方案变更 / 预算变更 / 周期变更 |

| 变更缘由 | 必须说明业务发生重大变动等客观原因 |

| 原方案描述 | — |

| 变更后方案 | — |

| 影响分析 | 对预算、周期、功能的影响 |

| 附件 | 变更后的详细方案 |

  

- 系统记录所有变更历史，支持变更前后对比

  

#### 5.2.5 延期管理

  

**功能点：**

- 项目原则上不得延期（对应第三十一条）

- 确需延期的，**提前30个工作日**以书面形式提交延期申请

- 延期申请需说明客观原因

- **延期时间一般不超过半年**

- 系统自动监控：

  - 延期超半年的项目 → 自动标记为负面清单项目 → 报领导小组

  - 因二级单位疏于管理、推进不力造成延期的 → 系统预警

  

**界面设计要素：**

- 延期申请表单：延期原因、拟延期时长、影响说明

- 审批流程：信息办审批 → 领导小组办公室备案

- 预警看板：列出所有延期项目及延期天数

  

#### 5.2.6 项目终止管理

  

**功能点：**

- 触发条件（对应第三十四条）：国家政策法规变化、学校战略规划调整、资金短缺、厂商变故、技术落后且无法调整

- 终止流程：

  

```

经办人提交终止申请 → 说明原因、已完成工作、费用情况、资产处置建议

    → 编制终止报告 → 信息办审核 → 领导小组审批 → 下达终止通知

    → 费用清算（会同财务部、国资处、审计处）→ 资产清查处置

    → 资料归档移交信息办

```

  

- 系统记录完整的终止过程文档

## 六、第五步：项目验收模块

  

### 6.1 业务流程

  

```

项目建设完成 → 承建方提交验收材料 → 二级单位内部初验

    → 初验合格 → 试运行（≥1个月）→ 提交正式验收申请

    → 信息办组织验收 → 验收评审 → 验收合格/不合格

    → 合格：文档归档、资产移交、使用推广

    → 不合格：限期整改 → 重新验收（二次不通过则半年后再提）

```

  

### 6.2 功能模块详细设计

  

#### 6.2.1 验收材料管理（承建方 + 二级单位）

  

**功能点：**

- 承建方在线提交验收材料包：

  

| 材料类别 | 具体内容 |

|---|---|

| 项目文档 | 需求规格说明书、设计文档、测试报告、用户手册 |

| 功能清单 | 合同约定功能 vs 实际交付功能对照表 |

| 性能测试报告 | 系统性能、压力测试结果 |

| 数据报告 | 数据准确性、完整性检查报告 |

| 培训记录 | 用户培训计划、培训签到、培训效果评估 |

| 安全报告 | 网络安全检测报告、漏洞扫描报告 |

| 源代码/部署文档 | 源代码交付清单、部署架构图 |

  

- 系统自动比对合同约定的建设内容与交付内容，标记差异项

  

#### 6.2.2 内部初验（二级单位操作）

  

**功能点：**

- 二级单位根据合同和承建方提交的材料进行内部初验（对应第三十七条）

- 初验内容：

  

| 初验维度 | 检查项 |

|---|---|

| 功能检查 | 各功能模块是否按需求实现 |

| 性能检查 | 响应速度、并发能力、稳定性 |

| 数据准确性与完整性 | 数据导入/导出是否准确完整 |

| 用户培训 | 培训是否覆盖所有使用人员 |

| 文档资料 | 文档是否齐全、规范 |

  

- 初验结果：合格 / 不合格（需填写不合格项及整改要求）

- 初验合格后，可申请正式验收

  

**界面设计要素：**

- 初验检查清单：勾选式检查表，每项可填写检查结果和备注

- 不合格项管理：列出不合格项，分配整改责任人，跟踪整改进度

- 初验报告生成：自动生成初验报告

  

#### 6.2.3 试运行管理

  

**功能点：**

- 初验合格后，系统强制要求**试运行不低于1个月**（对应第三十八条）

- 试运行期间记录：

  - 系统运行日志（异常、故障、性能数据）

  - 用户反馈与问题记录

  - 问题修复情况

- 试运行满1个月且无重大问题后，方可提请正式验收

- 系统自动计算试运行天数，不满足时禁止提交验收申请

  

**界面设计要素：**

- 试运行倒计时：显示已试运行天数/要求天数

- 问题记录表：试运行期间发现的问题及处理情况

- 用户反馈收集：简化的满意度评分和文字反馈

  

#### 6.2.4 正式验收组织（信息办操作）

  

**功能点：**

  

**A. 验收申请受理：**

- 二级单位提交正式验收申请，系统自动校验：

  - 内部初验是否合格

  - 试运行是否满1个月

  - 验收材料是否齐全

- 校验通过后，信息办受理

  

**B. 验收小组组建：**

- 信息办组织专家成立验收小组

- 系统根据项目级别提示专家要求：

  

| 项目级别 | 专家要求 |

|---|---|

| 重大（≥500万） | 校外专家须超过一半 |

| 重大（<500万） | 校外专家不少于2人 |

| 其他 | 按论证要求配置 |

  

- 验收方式：听取汇报、查阅资料、实地查看、满意度调查

  

**C. 验收评估维度（对应第三十八条）：**

  

| 评估维度 | 说明 |

|---|---|

| 建设目标达成度 | 是否实现申报书中的建设目标 |

| 技术指标 | 是否达到合同约定的技术指标 |

| 运行效果 | 系统运行稳定性、性能表现 |

| 用户体验 | 界面友好度、操作便捷性 |

| 数据对接共享 | 是否实现跨部门数据对接与共享 |

| 使用培训 | 培训是否充分，用户是否掌握 |

| 维保任务 | 维保方案是否完善 |

| 网络安全 | 安全防护是否到位 |

| 经费使用 | 经费使用是否合规 |

  

- 系统提供在线评分表和文字意见填写功能

- 验收结论：**合格 / 不合格**

  

**D. 验收结果处理：**

- **合格**：系统生成验收报告，进入项目移交流程

- **不合格**：依据整改意见限期整改后重新验收

- **二次验收仍未通过**：进行整改，**半年后方可再次提出验收**（对应第三十九条）

- 系统自动锁定二次不通过的项目，半年后才开放再次验收申请

  

#### 6.2.5 项目移交与推广（二级单位操作）

  

**功能点：**

- 验收合格后：

  - **文档资料归档**：系统自动归档所有项目文档（需求、方案、合同、验收报告等）

  - **资产移交/登记**：与学校资产管理系统对接，办理资产移交手续

  - **使用推广**：记录推广计划、推广范围、推广效果

  

**界面设计要素：**

- 归档清单：自动汇总所有应归档文档，标记归档状态

- 资产登记表：自动提取硬件/软件资产信息，对接资产系统

- 推广计划：推广范围、时间节点、负责人

## 七、第六步：项目运维模块

  

### 7.1 业务流程

  

```

项目验收完成 → 组建运维团队 → 制定运维管理规范

    → 日常运维（巡检/故障处理/安全维护/数据备份）

    → 用户支持与培训 → 运维评估 → 维保期管理

```

  

### 7.2 功能模块详细设计

  

#### 7.2.1 运维团队管理（二级单位操作）

  

**功能点：**

- 验收完成后，二级单位联合承建厂商组建运维团队（对应第四十条）

- 维保期满后可继续购买运维服务

- 运维团队信息：

  

| 字段 | 说明 |

|---|---|

| 团队名称 | — |

| 成员列表 | 姓名、角色、技术资质、联系方式 |

| 职责分工 | 各成员负责的系统模块 |

| 承建方联系人 | 维保期内的厂商对接人 |

| 维保期限 | 起止日期 |

| 续购状态 | 已到期/已续购/服务中 |

  

#### 7.2.2 运维管理规范（二级单位操作）

  

**功能点：**

- 运维团队制定完善的运维管理规范（对应第四十一条），系统提供模板引导：

  

| 规范模块 | 内容要求 |

|---|---|

| 系统巡检 | 巡检频率、巡检内容、巡检方法 |

| 故障处理 | 故障分级（P0-P3）、响应时间、处理时限 |

| 安全维护 | 安全策略、补丁管理、漏洞修复 |

| 数据备份与恢复 | 备份策略（全量/增量）、备份频率、恢复流程 |

| 设备更新升级 | 升级计划、升级流程、回滚方案 |

| 用户支持与培训 | 支持渠道、培训计划 |

| 应急预案 | 各类故障的应急处理流程 |

  

- 规范文档上传至系统存档

- 支持版本管理（规范更新时保留历史版本）

  

#### 7.2.3 系统巡检管理

  

**功能点：**

- 运维团队定期对信息化项目进行全面巡检（对应第四十二条）

- 巡检内容：

  

| 巡检类别 | 检查项 |

|---|---|

| 硬件设备状态 | 服务器性能、网络设备运行参数、存储容量 |

| 软件系统功能 | 业务模块运行、数据交互、接口调用 |

| 安全漏洞 | 系统漏洞扫描、网络安全配置、恶意软件检测 |

  

- 系统提供巡检模板，运维人员在线填写巡检记录

- 巡检结果自动生成巡检报告

- 发现问题自动关联至故障处理流程

  

**界面设计要素：**

- 巡检日历：展示巡检计划和完成情况

- 巡检表单：按类别分组的检查项（通过/异常/需关注）

- 异常项自动创建工单

  

#### 7.2.4 故障报修与处理

  

**功能点：**

- 建立故障快速响应机制（对应第四十三条）

- **多渠道报修**：系统内工单、电话记录、邮件转工单

- 故障分级：

  

| 级别 | 定义 | 响应时间 | 处理时限 |

|---|---|---|---|

| P0-紧急 | 系统完全不可用，影响全校 | 15分钟 | 2小时 |

| P1-严重 | 核心功能不可用 | 30分钟 | 4小时 |

| P2-一般 | 部分功能异常 | 2小时 | 24小时 |

| P3-轻微 | 体验问题，不影响使用 | 8小时 | 72小时 |

  

- 故障处理流程：

  

```

用户报修 → 创建工单 → 运维团队认领 → 故障诊断 → 故障修复

    → 用户确认 → 工单关闭 → 总结分析

```

  

- **重大故障**：需及时上报信息办与领导小组办公室（系统自动触发通知）

- 故障处理过程中，系统自动向师生用户通报进展（通过系统通知）

- 故障修复后，生成详细的故障报告（原因分析、处理过程、预防措施）

  

**界面设计要素：**

- 工单看板：按状态分类（待处理/处理中/待确认/已关闭）

- 工单详情：报修信息、处理记录、时间线

- 重大故障升级按钮：一键上报信息办和领导小组办公室

- 故障统计仪表盘：按级别/项目/时间维度统计

  

#### 7.2.5 数据备份管理

  

**功能点：**

- 制定严格的数据管理机制（对应第四十四条）

- 备份策略配置：

  

| 配置项 | 说明 |

|---|---|

| 备份类型 | 全量备份 / 增量备份 |

| 备份频率 | 每日/每周/每月 |

| 备份存储位置 | 异地安全存储介质 |

| 备份保留周期 | — |

| 恢复测试频率 | 定期验证备份数据可恢复性 |

  

- 系统记录每次备份操作（时间、类型、大小、状态、存储位置）

- 恢复测试记录：测试时间、测试结果、发现问题

- 备份异常自动告警

  

#### 7.2.6 用户支持与培训

  

**功能点：**

- 为用户提供操作指导与问题解答服务（对应第四十五条）

- 培训管理：

  

| 功能 | 说明 |

|---|---|

| 培训计划 | 培训内容、时间、对象、方式 |

| 培训记录 | 签到、培训材料、视频回放 |

| 效果跟踪 | 定期回访、在线问卷调查 |

| 需求收集 | 用户对系统功能的掌握程度和新需求 |

  

- 培训效果长期跟踪机制：通过定期回访、问卷调查收集反馈

- 反馈分析：据此调整培训内容和方式

  

#### 7.2.7 运维评估与报告

  

**功能点：**

- 系统自动生成运维月报/季报/年报，内容包括：

  - 巡检完成率

  - 故障统计（数量、级别、平均响应时间、平均修复时间）

  - 备份执行率

  - 用户满意度

  - 运维改进建议

- 支持运维KPI看板
