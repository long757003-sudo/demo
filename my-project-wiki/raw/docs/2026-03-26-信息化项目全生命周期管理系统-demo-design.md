## 一、项目背景

基于西南大学信息化项目管理办法设计的演示 Demo，覆盖信息化项目从需求征集到运维的完整生命周期，共涉及 **12 个业务角色**、**8 个生命周期阶段**、**45 条业务规则**。

### 演示案例

> **项目名称**：本科教学质量分析平台
> **申请单位**：教务处
> **项目负责人**：李明
> **预算金额**：85 万元（小型项目）
> **项目背景**：当前教学质量数据分散在多个系统，缺乏统一分析平台
> **适用流程**：小型项目完整流程——专家 3 人论证、领导小组办公室审定、采购走挂网采购

## 二、技术方案

| 项目      | 决策                                |
| ------- | --------------------------------- |
| Demo 形态 | 可点击原型（假数据，无真实后端）                  |
| 技术栈     | 纯 HTML / CSS / JavaScript，无构建工具   |
| 文件组织    | 单文件 SPA：`app.html` + `shared/` 目录 |
| 打开方式    | 浏览器直接打开 `app.html`，无需本地服务器        |
| 数据存储    | `localStorage`（角色状态、表单草稿）         |
| 部署方式    | 直接复制文件夹即可演示，零依赖                   |

### 文件结构

```
demo/
├── index.html              # 角色选择/登录页
├── app.html                # 主 Shell（左侧菜单 + 右侧内容区）
└── shared/
    ├── nav.js              # 左侧菜单构建（角色感知）
    ├── router.js           # Hash 路由（切换视图）
    ├── data.js             # 全局假数据
    └── style.css           # 全局样式
```

所有 40 个视图均作为函数定义在 `app.html` 内，通过 hash 路由切换，左侧菜单始终固定。

## 六、页面模板（4 种）

### T1 · 仪表盘模板
用于工作台首页。构成：
- **统计卡片行**：待办事项数 / 在建项目数 / 即将超期数 / 待我审批数（按角色变化）
- **待办事项区**：角色相关的待办清单，超期项标红
- **项目动态区**：最近项目状态变化
- **系统通知区**（右侧）：三级通知
  - 🔴 逾期预警（红色左边框）
  - 🟡 截止提醒（黄色左边框）
  - 🔵 流程通知（蓝色左边框）
  - 每条通知含时间戳和发送来源，右上角显示未读角标

### T2 · 列表模板
用于所有管理列表页。构成：
- **搜索筛选栏**：关键词搜索 + 多个下拉筛选 + 查询按钮 + 新建按钮
- **数据表格**：含分页（每页 10 条）
- **可排序列**：预算金额（↑↓）、申报日期（↑↓）、截止日期（↑↓），点击列头切换升/降序，当前排序列标蓝
- **截止日期**：临近 7 天标橙，超期标红

### T3 · 表单模板
用于所有填报/申请页。构成：
- 表单标题（文件名称）
- 分组字段（两列栅格布局），必填字段标 `*`
- 预算金额字段自动识别并展示项目类型（微型/小型/中型/重大）
- 底部：「暂存草稿」+「提交审核」按钮

### T4 · 详情模板
用于项目详情页及审批操作页。构成：
- **项目头部**：项目名称 + 当前阶段标签 + 操作按钮（按角色和阶段动态显示）
- **生命周期进度条**：6 个节点（需求征集→立项论证→采购→实施→验收→运维），当前阶段高亮蓝色，已完成绿色，未开始灰色
- **审批流时间轴**：各审批节点状态（已完成/进行中/待处理）
- **详情内容区**：基本信息、关联文档列表
- **操作记录 Tab**（所有 T4 页面均包含）：该记录的完整变更时间轴，每条记录含操作时间、操作人、操作类型（创建/提交/审批通过/驳回/修改/重新提交）、修改字段的 before/after 对比；只读，不可删除或修改

## 九、演示场景脚本（建议顺序）

演示时按以下角色切换顺序走完一个完整项目流程：

```
【需求阶段】
① 信息办管理员    → 发起2025年度需求征集，系统自动发送「需求征集通知」给各单位系统管理员
② 单位系统管理员  → 收到通知后，在系统中手动指派需求填写人（授权），被授权人才可填写
③ 项目负责人(李明)→ 获得授权后，填写「本科教学质量分析平台」需求申请并提交
④ 单位系统管理员  → 对本单位需求进行优先级排序后提交
⑤ 单位分管领导    → 审核通过，提交信息办
⑥ 信息办领导     → 需求遴选，通过本项目需求

【立项阶段】
⑦ 信息办管理员   → 从通过遴选的需求中选择本项目，联动发送「立项申请通知书」给李明
⑧ 项目负责人     → 收到通知书后，填报申报书（预算85万，系统自动识别为小型项目）
⑨ 信息办管理员   → 从专家库选择3位专家（校内2+校外1），提交信息办领导确认
⑩ 信息办领导     → 确认专家名单，系统自动发送「专家评审邀请」通知给各专家
   ↳ 若专家拒绝  → 返回⑨重新选专家 → ⑩领导确认 → 系统重发邀请（循环至全部接受）
⑪ 专家委员会     → 全部接受邀请，评审任务正式发起；各专家填写论证意见
   ↳ 论证不通过  → 项目负责人按专家意见修改申报书，重新提交二次论证
   ↳ 二次仍不通过→ 项目状态变为「冻结」，一年后方可重新发起（BR-06）
⑫ 领导小组办公室 → 论证通过后，审定立项
⑬ 信息办管理员   → 下达立项通知书，系统自动发送「立项通知书」给李明

【采购阶段】
⑭ 项目负责人     → 填写采购调研报告（至少3家供应商，系统校验BR-17）
⑮ 信息办         → 技术审核通过，系统通过接口自动调取招采系统中对应的招标文件、应标文件等信息，展示在采购管理页面
⑯ 合同管理员     → 基于招采结果进行合同审定，归入合同台账

【实施阶段】
⑰ 项目负责人     → 按合同支付节点要求，逐节点提交对应阶段文档材料（以合同约定为准）

【验收阶段】
⑱ 项目负责人     → 内部初验填报（系统校验试运行≥1个月BR-15）
⑲ 信息办管理员   → 选择验收专家，提交信息办领导确认
⑳ 信息办领导     → 确认专家名单，系统自动发送验收评审邀请
   ↳ 若专家拒绝  → 返回⑲重新选专家（循环至全部接受）
㉑ 专家委员会     → 全部接受邀请，填写验收意见（通过），生成验收报告

【运维阶段】
㉒ 财务管理员     → 查看经费使用情况（合同进度款支付节点 + 年度预算使用总览）
㉓ 项目负责人     → 填写运维记录（巡检、数据备份）
㉔ 项目负责人     → 提交故障工单（演示故障处理流程）
㉕ 信息办领导     → 查看「系统使用情况」仪表盘，评估项目建设目标达成情况
    （展示：活跃用户数、功能使用率、数据量趋势、满意度评分、与建设目标对比）
```

### 通知模块联动机制

通知管理支持两种使用方式：

**独立使用**：从「通知管理 → 通知列表」直接新建任意类型通知。

**通知类型说明**（立项环节有两种不同通知，需严格区分）：

| 通知类型 | 发送时机 | 发送人 | 接收人 |
|---------|---------|--------|--------|
| 需求征集通知 | 需求征集发起时 | 信息办管理员 | 各单位系统管理员 |
| 立项申请通知书 | 需求遴选通过后，邀请填报申报书 | 信息办管理员 | 被选中需求的项目负责人 |
| 专家评审邀请 | 信息办领导确认专家名单后 | 信息办管理员 | 受邀专家 |
| 立项通知书 | 领导审定通过后，正式确认立项 | 信息办管理员 | 立项项目的项目负责人 |

**模块联动**（其他模块触发跳转）：

| 触发模块 | 触发操作 | 跳转行为 |
|---------|---------|---------|
| 发起需求征集 | 点击「保存并发送通知」 | 携带征集标题/截止日期，跳转页面36，类型预填「需求征集通知」，收件人预填各单位系统管理员 |
| 需求遴选 | 点击「发送立项申请通知书」 | 携带已选需求项目名称，跳转页面36，类型预填「立项申请通知书」，收件人预填对应项目负责人 |
| 发起评审（领导确认后） | 系统**自动**发送，无需手动触发 | 系统自动发送「专家评审邀请」给已确认的专家名单，不经过页面36 |
| 下达立项通知 | 点击「生成并发送立项通知书」 | 携带项目名称/立项结论，跳转页面36，类型预填「立项通知书」，收件人预填项目负责人 |

联动通知发送后，原模块页面显示「通知已发送 · 查看详情 →」跳转链接至页面37。

**防纠纷设计**：页面37（通知发送详情）记录每位收件人的送达时间和已读时间，支持导出为 PDF/Excel，作为通知已送达的凭证。
